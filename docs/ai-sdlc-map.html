Field map · from the AI-Native SDLC Playbook

Six stages, one loop, a gate at every handoff

Each stage commits an artifact that the next stage reads. Each handoff has a gate, held by a named person or by a deterministic check. The agent acts up to the production gate and cannot pass it.

◆ human gate (named approver) ■ deterministic gate (check must pass) entry-point play, needs nothing first

03 · Stage by stage

What must be true, who signs, how you measure it

STAGE 1

Plan

Capture as intent.md
  • The originator brainstorms with Claude in their own words until the idea is concrete
  • A template skill structures it: problem, outcome, users and systems, constraints, open questions
  • Committed to a watched intent/ home. A VCS connector commits for people who don't use git
  • The product owner corrects every agent-written intent before commit
◆ Gate: product owner. Merge = accept, closed review = reject.
Leading
First conversation → committed intent (weeks → hours)
Lagging
Intent survival rate; intent edits after the first spec.md
STAGE 2

Design

Requirements and design
  • Brand, security, compliance and UX policies are loaded as skills
  • The prompt demands flagged concerns, including policies that contradict each other
  • Automation path: by hand → org slash command → job on intent merge that opens a spec.md PR
  • Concerns are resolved with named policy owners before engineering sees the spec
  • The spec, its prompt and the skill versions in force are all in git
◆ Gate: product owner; tech lead for higher-risk changes.
Leading
intent.md commit → spec.md commit
Lagging
spec.md commits dated after the first plan.md (rework)
STAGE 3

Build

Plan mode · auto mode · CLAUDE.md · skills · hooks · parallel sessions
  • plan.md names the files, the order and the proving tests, and is updated in the same commit when the work drifts
  • CLAUDE.md stays under a page. A mistake made twice goes into it
  • Skills are tested for triggering and signed off by the policy owner. Must-hold policies get a hook as backstop
  • Build hooks are fast and scoped to the file. No "ask" hooks during build
  • Start with 2–3 worktrees. The verifier subagent reports only and never fixes
  • Auto mode only with a tight spec, a small blast radius and existing test coverage
◆ Gate: engineer accepts the plan; tech lead or architect if higher-risk.
Leading
% merged from the first pass; plan approved → PR merged; repeated mistakes; policy → skill merge time; sessions per engineer
Lagging
Rework cycles; diff ↔ plan.md match; new joiner's first PR; policy-citing findings → zero; merges per week vs. rework
STAGE 4

Test

Feedback loop · continuous evals in CI
  • Test and build each run with one command that exits non-zero on failure. Healthy output is listed in CLAUDE.md
  • Bug fixes: commit the failing test first. A hook blocks edits to test files during the fix
  • "Done" means the test output is pasted. UI work loops on screenshots against the mock
  • 20–50 real-task evals run nightly and on any change to CLAUDE.md or .claude/**
  • The pass rate is a merge check. Every incident becomes an eval
■ Gate: eval pass-rate threshold; code owner reviews with evidence attached.
Leading
First-pass CI success; eval pass rate; incident → eval time
Lagging
Review time per PR; change failure rate; regressions caught in CI vs. in prod
STAGE 5

Deploy

PR review · approval-gate hooks · managed settings · CI/CD
  • REVIEW.md defines three passes (bugs, security, compliance with spec/plan) and caps nits at 5
  • Findings never approve. Branch protection requires a code owner
  • An @claude fix loop, or a babysit command that drives Claude's own PRs to green. Tuning is monthly
  • Gates are hooks. Non-negotiable ones live in managed settings, and every block explains itself
  • Rollback is a single command, rehearsed in staging
◆ Gate: code owner merges; a named release manager authorizes production.
Leading
Time to first review → minutes; comments resolved hands-off; wait time per gate; failures triaged without paging
Lagging
Defects caught vs. escaped; gate violations in prod; DORA
STAGE 6

Maintain

Closing the loop · Claude Tag on call
  • Monitor one metric with a stable rolling baseline. The detector is deterministic and unit-tested
  • Tiers live in bands.yaml: 1σ logs, 2σ diagnoses read-only, 3σ opens a PR or runs a pre-approved runbook
  • Findings come back as intent.md. Triage is fix, schedule or dismiss; dismissals tune the bands
  • In Slack, Claude waits for a human "Go", confirms the metric is back in band, and writes a lessons file
◆ Gate: service owner triages; fixes take the normal PR gate.
Leading
Band breach → intent.md in the triage queue
Lagging
% of findings merged as fixes; repeat incidents of the same class

06 · Maintain

Detection is deterministic; the tier decides what Claude may do

band breach→ Claude writes intent.md with evidence→ ◆ owner triages: fix · schedule · dismiss→ normal stages + PR gate→ fix ships→ incident added as an eval

Measure the time from breach to intent.md in the triage queue, the share of findings that become merged fixes, and repeat incidents of the same class. Dismissals feed back into the band settings to cut noise.
