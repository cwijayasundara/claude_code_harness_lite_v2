# Spec v0.4: the autonomous ratchet

Status: approved · 2026-10-04 · extends `DESIGN.md` (v0.1), spec 1 (quality sensors) and v0.3. Based on the shop-app brownfield trial (2026-10-04), Anthropic's *AI-Native SDLC Playbook*, and a loop-vs-graph research pass (sources in §15).

## 1. Problem

The shop-app trial showed that the planning side works. A tier L change produced a testable spec (B1–B21), a plan with rejected alternatives and contracts, proof of red, and a review that caught a real contract regression. The stretch from an approved plan to a reviewed PR does not match how the person wants to work:

1. **Build and test keep asking for approval.** The settings hooks only ever `deny` or `ask`; nothing returns `allow`. `.claude/settings.json` pre-approves only `Edit(.sdlc/**)`, so every source edit and test run inside an approved plan still prompts.
2. **Review is a single pass after the build.** Implementers get no per-slice reviewer, there is one fix round for the whole change, and tier S/M review depended on a PR workflow that was never installed (fixed in `673e9dc`: review now stays in the session when no PR review can run).
3. **Testing is one undifferentiated command.** `sensors.json` declares `test` only. Nothing distinguishes or requires unit, integration, acceptance or API tests.
4. **The pre-PR sensors are partial.** The ship gate covers test tampering, suppressions, layering, size, secrets, rules and harness tampering. Nothing runs lint, types, dependency audit, coupling, complexity, SAST or performance against the base branch.
5. **The PR is manual and nothing reviews it.** Ship asks before `git push` and `gh pr create`, there is no `REVIEW.md`, and no review runs against the open PR.
6. **Measurement is mostly `unmeasured`.** 14 of 14 playbook metrics needed more samples or `gh`. Per-story cost exists only as a session total in the band, and value is not estimated at all.

## 2. Decisions made with the person

| Decision | Choice |
|---|---|
| Loop or graph | **Hybrid.** The lifecycle of a change is an explicit graph (a deterministic state machine whose state is the files on disk). Build, test, sensors and PR review are bounded loops inside graph nodes. |
| Approach | **A**: the graph in the script, the loops in the skills, the mod for the experience and as the driver. Rules never live only in the mod. |
| Human gates | Spec and plan are gated, **configurable per tier** in `sensors.json`. Defaults stay as today (L and greenfield gated, S and M not). Merge and deploy stay human. |
| Build to PR | **Autonomous.** No permission prompts inside an approved plan. The PR is created and reviewed automatically. |
| Measurement | Computed by the script (works in CI and headless runs), drawn by the mod, with text output as the fallback. |
| Cost and value | Both. Cost is measured. Value is an estimate from configurable baseline hours per tier times a rate, which the architect may refine at plan time. |
| Driver | A zero-token `/sdlc-next` in the mod advances node by node. The model-driven `/sdlc-next` skill stays as the fallback. Both call the same script function. |

## 3. Non-goals

- **Deploy and Maintain.** `ready` (PR open, reviewed, green) is the last node. The production gate, rollout and monitoring are a later spec.
- **An external orchestration runtime.** No LangGraph, Temporal or background daemon; a CLI plugin has nowhere to host one.
- **Unbounded loops.** Every loop has a round cap, stall detection and a dollar cap.
- **A model deciding when a loop ends.** Reviewers advise; deterministic checks (tests, sensors, invariants) decide.
- **Per-language code in `sdlc.ts`.** Sensor commands come from the project, with a starter table per stack in data.
- **Any change to who can approve.** Approvals and waivers stay human-only.

## 4. The graph

### 4.1 Nodes

```
intent ─▶ spec ─▶ plan ─▶ build ⟲ ─▶ test ⟲ ─▶ sensors ⟲ ─▶ pr ─▶ pr-review ⟲ ─▶ ready
          [gate?]  [gate?]                                                        (human merges)
any node ─(round cap | stall | broken invariant | budget)─▶ blocked (human)
```

- `[gate?]` is a human approval, applied per tier from `sensors.json` `"gates"` (§9.1).
- Change type and tier choose a subgraph, as `PATHS` does today. Bugfix keeps `diagnose` in place of `spec`. Spike stops at `intent` + `notes.md`. Chore and tier S skip `spec`.
- Today's `verify` stage becomes `test`, and today's `review` stage becomes `pr-review`. The artifacts keep their names and meaning (`verification.md`, `review.md`), so existing change folders resolve. A change folder with a `review.md` and no `ratchet.json` is read as v0.3.

### 4.2 The transition function

`next(slug) → { node, verdict: 'continue' | 'human' | 'blocked' | 'ready', reason }`. It is pure over the change folder, `approvals.jsonl`, git and `usage.jsonl`, makes no model call, and is unit-tested. `status`, `/sdlc-next` (skill and mod) and the auto-approval rule all call it.

| Edge | Guard |
|---|---|
| intent → spec / plan | `intent.md` has problem, outcome, non-goals and risks |
| spec → plan, plan → build | When gated: the approval digest matches the artifact. Always: `## Open questions` is `none` |
| build → test | Every slice in `plan.md` is done in `ratchet.json`. Each slice's last review has no critical/high finding, or its cap was reached with the findings recorded. The diff stays within `## Files` |
| test → sensors | `verification.md` is sdlc-generated with `result: pass`, and every **required** test level (§5.2) ran and passed |
| sensors → pr | No sensor category has more findings than the base branch (§5.3). Built-in sensors have no blocks |
| pr → pr-review | The branch is pushed and a PR is open, or `local-only` is recorded when there is no `origin` remote |
| pr-review → ready | `review.md` is `pass` or `accepted`. With a remote, the PR's checks are green |

### 4.3 State on disk

All under `.sdlc/changes/<slug>/`, written only by `sdlc.ts`. The pre-edit and pre-bash hooks deny model writes, as they do for `runs.jsonl` today.

- `ratchet.json`: per node, the round count, cap, and the hashes of each round's findings. Per slice, its status and rounds. Also the baseline test count and the base-branch sensor counts, keyed by the base SHA. JSON because models overwrite JSON less readily than Markdown (Anthropic, *Effective harnesses for long-running agents*).
- `events.jsonl`: one row per edge or loop round: `{ at, node, verdict, round, reason, tokens, usd }`. It also records every automatic approval: `{ at, kind: 'auto-approve', tool, target }`.
- `pr.md`: the PR scorecard (§7.3). It is the PR body when there is a remote, and the record when there is not.

### 4.4 Invariants

Breaking any one routes the change to `blocked`:

1. The test count never drops below the baseline.
2. No test is skipped, focused, weakened or deleted (the existing test-tamper sensor).
3. No sensor category rises above the base branch.
4. The diff never grows beyond the plan's `## Files` (the existing scope gate).
5. No node runs past its round cap or dollar cap.

### 4.5 `blocked`

`blocked` records the node, the reason, the last findings and the spend in `events.jsonl`, and `status` prints them with the next actions: fix and resume (`/sdlc-next`), waive (`/sdlc-waive`), or raise the cap for this change (`/sdlc-approve <slug> budget`, human-only).

## 5. The loops inside nodes

Each loop has the same shape: **act → deterministic checks → advisory review → fix**. It exits when its guard passes, and goes to `blocked` on its cap, a **stall** (a finding hash seen in the previous round, or a round with no diff progress) or its budget. Caps and budgets default from `sensors.json` `"ratchet"` (§9.1).

### 5.1 build ⟲ (per slice; default 2 fix rounds)

1. The `implementer` (Sonnet) writes the failing test, records the red run, implements, and records green, as today.
2. The `reviewer` (Opus), a separate agent, reviews **only that slice's diff** against the spec's B-numbers and the plan's `## Design` and `## Contracts`. It replies in the existing findings format, and `sdlc.ts ratchet record` hashes the findings into `ratchet.json`.
3. Critical and high findings go back to the same slice's implementer. Medium findings are deferred to `pr-review`.
4. Slices run one after another. They run in parallel (at most 3) only when the plan's file sets for those slices do not overlap.

### 5.2 test ⟲ (default 2 fix rounds)

`sensors.json` declares test levels: `"levels": { "unit": "<cmd>", "integration": "<cmd>", "acceptance": "<cmd>", "api": "<cmd>" }`. One command may serve several levels.

| Level | Required when |
|---|---|
| unit | always |
| acceptance | always for tier L and greenfield. Proven by traceability: every spec B-number has a named test |
| api | `plan.md ## Contracts` adds, renames or removes an endpoint |
| integration | the plan's `## Files` spans more than one top-level module, or a consumer repo is affected |

A required level with no declared command is `blocked: level <x> required but not declared`, never passed. The `verifier` runs every required level through `sdlc.ts run`, and `verify-report` writes the levels into `verification.md`. Only failing items go back to the implementer.

### 5.3 sensors ⟲ (default 1 fix round)

`sensors.json` `"quality"` declares command categories: `lint`, `types`, `deps` (audit and dependency breaks), `coupling` (import cycles, layering), `complexity`, `security` (SAST) and `perf` (benchmark, required only when the spec has a performance NFR). Each entry is a command plus how to count its findings: `{ "cmd": "...", "count": "exit" | "lines" | "json:<path>" }`.

- Each category runs on the branch, and its count is compared with the **base-branch count**. The base runs once in a temporary `git worktree` at the merge-base and is cached in `ratchet.json` by base SHA. In a brownfield repo this means "no regression", not "zero findings".
- A category with no command is `unmeasured` and shown as such. It never counts as passing.
- A command that crashes, times out or is not installed is `fail` with the reason recorded.
- The built-in sensors (test-tamper, suppression, layering, size, secrets, rules, harness-tamper, traceability, proof of red) also run, as the ship gate does today.

### 5.4 pr and pr-review ⟲ (default 1 fix round)

- **pr** (script-only, no model): commit as `ship` does today, push to `sdlc/<slug>`, and `gh pr create` with `pr.md` as the body. With no `origin`, record `local-only`.
- **pr-review**: `/code-review` at high effort, `/security-review` when tier L or the intent's risks name auth, payments, data, secrets or a public API, and the policy in a new **`REVIEW.md`** (playbook format: review passes, what counts as Important, exclusions). Findings are posted as one PR comment, each with a severity. One fix round, pushed to the same PR, then the checks are read with `gh pr checks`. The background `sdlc-review.yml` stays available as a second, independent reviewer.

### 5.5 Budgets

Before each round, `/sdlc-next` (skill or mod) asks `next()`, which sums the change's spend for that node from `usage.jsonl`. A node over its dollar cap goes to `blocked` with the spend shown.

## 6. No prompts inside an approved plan

### 6.1 Where the rule lives

In the **settings hooks**, not the mod: `pre-edit` and `pre-bash` gain an `allow` decision. A `PreToolUse` settings hook may return `allow`, which works in the terminal, `claude -p`, CI and cloud sessions, and does not depend on mods being enabled.

### 6.2 The rule

One pure function, `autoApprove(change, node, tool, input) → boolean`. It applies only when the active change's `next()` node is `build`, `test`, `sensors`, `pr` or `pr-review`, and every gate before that node has passed.

| Approved automatically | Never approved automatically |
|---|---|
| Write/Edit to a path inside `## Files` that is not a harness or evidence file | Harness and evidence files; anything outside `## Files` |
| Commands declared in `sensors.json` (`fast`, `full`, `levels`, `quality`), run directly or via `sdlc.ts run` | Any other command |
| `git add`, `git commit`, `git checkout -b sdlc/<slug>`, `git push origin sdlc/<slug>` | Pushing to the trunk; `--force`; `git reset --hard` |
| In `pr`/`pr-review`: `gh pr create`, `gh pr comment`, `gh pr checks`, `gh pr view` for this PR | `gh pr merge`; any other `gh` write |

The hook only turns `ask` into `allow`. It never overrides a `deny` rule or one of its own `deny` decisions. Each automatic approval is appended to `events.jsonl`, and the PR scorecard counts them.

## 7. Measurement

### 7.1 Where the numbers live

`sdlc.ts metrics` computes everything from `events.jsonl`, `usage.jsonl`, `approvals.jsonl`, git, `gh` (when a remote exists) and `.sdlc/incidents/`. The mod draws the numbers. Text is the fallback.

### 7.2 Indicators

| Stage | Leading | Lagging |
|---|---|---|
| Plan | intent → approved (h) | intent survival rate |
| Design | intent → spec (h) | spec commits after plan approval |
| Build | slices passing review at round 0; plan approval → PR (h) | fix rounds per change; diff matches plan |
| Test | required levels passing at round 0; first-pass CI | regressions caught before merge vs escaped |
| Sensors | findings fixed before the PR | base-branch findings trend |
| Review | time to first review (min) | defects caught vs escaped |
| Autonomy | share of tool calls auto-approved; escalations per change | share of changes reaching `ready` with no human except the gates |
| Economics | $ and tokens per node; spend vs budget | $ per merged change; estimated value ÷ cost; cache-hit share |

Repo-level metrics keep `MIN_SAMPLE` (5) and read `unmeasured (n<5)` below it. Per-story numbers are raw.

### 7.3 Views

1. **Per story (live):** the band and the story pane (§8).
2. **Per PR:** `pr.md`, a scorecard with rounds per node, test levels, sensor deltas against the base, auto-approved vs asked, tokens, cost, estimated value and escalations.
3. **Per repo:** `/sdlc-metrics` text, and a metrics pane with a tab per stage.

### 7.4 Cost and value

- **Cost:** the main thread's cost is the session ledger's delta per turn (as today, with the reset fix in `673e9dc`). Subagent cost is tokens × a price table in `scripts/` keyed by model, attributed by `turn.step` to the change and node active at request time.
- **Value (estimate):** `rate × hours[tier]` from `sensors.json` `"value"`. The architect may set `value_hours: <n> because <reason>` in `plan.md`, which overrides the tier default. Every display says "estimate".

### 7.5 The harness ratchets itself

- A finding category recurring 3 or more times suggests a rule (exists today).
- A node hitting its cap in 3 or more of the last 10 changes suggests raising the cap or adding a guide.
- A cap never reached in the last 10 changes suggests lowering it.

## 8. The mod

Rules stay in the script and settings hooks. The mod draws, drives and asks.

1. **Story band** above the prompt: `sdlc · <slug> · <node> ⟲<round>/<cap> (slice i/n) · <tokens> · $<cost> · value ≈ $<v> · sensors ✓|✗`.
2. **Story pane** (`/sdlc-story`): the graph with ✓ / ⟲ round/cap / ⛔ per node, tokens and $ per node and per agent type, value ÷ cost, deferred findings, and when blocked the reason with buttons **Open review**, **Waive…**, **Stop**.
3. **Metrics pane** (`/sdlc-metrics` in the terminal): a tab per stage from `sdlc.ts metrics --json`.
4. **Driver:** a zero-token `/sdlc-next` command runs `next()` and submits the node's skill prompt as if typed. On `turn.complete` it calls `next()` again: `continue` submits the next node, `human` shows the gate dialog, `blocked` and `ready` stop with a toast. The pane has **Run to next gate** and **Pause**. Between nodes, the mod suggests `/compact` past the soft context limit (state is on disk).
5. **Gate dialogs:** at a human node, `ui.ask` offers **Approve <stage> / Open <artifact> / Not yet**. Approval runs only from the person's choice, as the impact dialog does today. Headless runs print `human gate: /sdlc-approve …`.
6. **Usage capture per request** with `turn.step`, so subagent tokens land on the right change and node.

If the mod is off, fails or cannot draw, everything still works: approvals come from the settings hooks (§6), `/sdlc-next` is the skill, and metrics are text.

## 9. Configuration and onboarding

### 9.1 New `sensors.json` keys

```json
{
  "gates": { "S": [], "M": [], "L": ["spec", "plan"], "greenfield": ["spec", "plan"] },
  "levels": { "unit": "npm test", "acceptance": "npm test", "api": "npm test" },
  "quality": { "lint": { "cmd": "npx eslint .", "count": "lines" }, "deps": { "cmd": "npm audit --json", "count": "json:metadata.vulnerabilities.total" } },
  "ratchet": { "build": 2, "test": 2, "sensors": 1, "pr-review": 1, "usd": { "build": 6, "test": 2, "sensors": 2, "pr-review": 2 } },
  "value": { "rate": 100, "hours": { "S": 2, "M": 8, "L": 24 } }
}
```

Weakening any of these (removing a gate, raising a cap or budget, dropping a level or category) is harness-tamper and needs the person, as `weakensConfig` already does for limits.

### 9.2 Brownfield onboarding

1. Scouts detect the stack. `/sdlc-onboard` proposes `levels` and `quality` commands from a starter table per stack (data in `templates/stacks.json`), and the person confirms them.
2. **Baseline:** every level and quality command runs once on the trunk. Counts are stored as the base. Already-failing commands go into `knownRed`. The first full security scan is the recorded baseline.
3. Refactor changes require characterization tests first: the build node requires a passing run of the new characterization tests, recorded before any source file is edited.
4. Onboarding **installs and verifies** `sdlc-check.yml`, `sdlc-review.yml` (if wanted), `REVIEW.md` and the mod, and reports each as installed, skipped by the person, or failed.

### 9.3 Greenfield onboarding

The same starter table applied from the first commit. The walking skeleton has the lint, types, deps and security commands and one test per level, all green, before the first change.

### 9.4 Standalone repos and the mod

`vendor --standalone` copies the mod as a project-local plugin and registers it in `.claude/settings.json`, **if Claude Code supports a plugin inside the project** (verify, §13). If not, standalone repos get everything except the drawing and the zero-token driver.

## 10. Failure handling

- Every failure ends in a named state. A sensor or level command that crashes, times out or is missing is `fail` or `unmeasured`, never `pass`.
- `blocked` always names the node, the reason, the findings and the spend.
- No remote: `pr` records `local-only`, `pr-review` reviews the local branch, and the scorecard stays in `pr.md`.
- A mod failure falls back to permission prompts and the skill driver. The auto-approval is in the settings hooks, so it survives a mod failure.
- The Stop gate stays a safety net, at its existing 2 blocks per turn.

## 12. Footprint

The harness is about 4,240 lines against its own 5,000-line budget (`scripts/size.spec.ts`). This spec adds roughly 1,000–1,300 lines. **Decided with the person (2026-10-04):** the budget rises to 6,000 lines; the per-file limits are unchanged (scripts ≤ 500, mod files ≤ 300, skills ≤ 60).

## 13. To verify while implementing

1. A `PreToolUse` settings hook returning `allow` skips the permission prompt in an interactive session, and does not override `deny` rules, on the current Claude Code version.
2. A mod can submit a prompt as if typed (the API name and whether it works mid-session).
3. Whether a project can ship a plugin inside its own repo and enable it from `.claude/settings.json`.
4. `turn.step` usage carries `agentId` for subagents' requests, and the model needed for pricing.
5. A temporary `git worktree` for the base-branch sensor run is fast enough on shop-app and on a mid-size repo (target: under 60 s, cached per base SHA).

## 14. Proof

1. **Unit:** `next()` over fixture change folders for every type × tier; `autoApprove` allow and deny tables; each invariant; stall detection; value calculation; base comparison counting.
2. **Gate:** the hooks return `allow` only inside an approved plan, and never for harness files, the trunk or `--force`.
3. **Mod:** `claude plugin test` for the band, pane, driver (continue, human, blocked, ready), gate dialog and fallback when a call fails.
4. **End to end on shop-app:** redo `catalog-search-endpoint` from an approved plan, checking that:
   - no permission prompt appears between plan approval and `ready`;
   - every loop stops at or before its cap;
   - the `pr.md` scorecard's tokens and $ match `usage.jsonl`;
   - the change reaches `ready` with a PR (or `local-only`).
