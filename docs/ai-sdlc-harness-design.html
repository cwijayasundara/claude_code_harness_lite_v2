Design · 2026-10-07 · decisions taken, ready for planning

Closing the gaps between rig and the AI-Native SDLC Playbook

rig v0.6.0 already implements the playbook's core: the artifact chain, type × tier routing, human-only gates, deterministic sensors, a CI judge that cannot be weakened by the PR it judges, and the twelve metrics. This design maps every checklist item in docs/ai-sdlc-checklist.md to what rig has, and designs only what is missing. It keeps rig's principles, adds nothing to the core checker that a CI template can carry, and respects the 6,900-line budget.

01 · Understanding (please correct)

What this is for

Goal
Make a repo onboarded with rig satisfy every item in the checklist, including the worked example on p.42–43, CI/CD, and maintenance, so a team can run the playbook end to end on Claude Code.
Who
Engineering teams using rig, and a platform team that deploys managed settings and CI.
Success
Every checklist row reads covered with a named component, and every playbook metric is computed by sdlc.ts metrics rather than estimated.
Constraints you gave
Keep rig as simple and lean as possible. Every item below passes a lean test: it is a template (zero core lines), a change to an existing skill, or a leaf script under 200 lines; anything else is cut or deferred. Model by tier: tier S on Haiku 5.5 (claude-haiku-5-5, $0.10 in / $0.50 out per M tokens), tier M on Sonnet 5.5, tier L on Opus 5.5, for every model step of a change (design, implementation, review, CI review, spec job). Steps that are not tied to a change (code search, triage, watch diagnosis, the review sweep) run on Haiku.
Decisions taken
(1) Everything lands in core; the line cap rises from 6,900 to 7,600, and the design must fit it, templates included, because size.spec.ts counts them. (2) Evals are run by a person, never on a schedule or a PR trigger. (3) The intent inbox is .sdlc/intent/. (4) Model by tier, as above. (5) The production gate may match command text, as the playbook's script does.
Constraints I assume
No hook on Bash in the core (DESIGN §9). New parts add no imports to check, hooks or sdlc's hot path (ROADMAP's v3 rule). Windows stays unsupported. Claude Tag (Slack) is a thin integration, not a dependency.
Not in scope
The DeepWiki and learning loops from ROADMAP.md. A rewrite of any existing stage. Moving artifacts out of .sdlc/.

Six items are real gaps. Under the lean rule, only two of them need code in rig (evals.ts and watch.ts, both leaf scripts); the other four are templates, one SKILL.md, and edits to skills that already exist.

Model routing: one rule, tier picks the model

Decision 4: S → Haiku 5.5, M → Sonnet 5.5, L (and greenfield) → Opus 5.5, applied to every model step that belongs to a change. The mechanism is one thing rig does not do today: agents carry a fixed model:, and no skill sets one (a model switch re-reads the context uncached, DESIGN §2.7). The mechanism is the Agent call's own model parameter, which rig already uses (the build skill's tier L slice review passes model: sonnet) and which takes precedence over an agent file's model:. sdlc.ts next --json gains a model field derived from the change's effective tier; every skill passes it on each architect, implementer and reviewer launch. The template pins the aliases (ANTHROPIC_DEFAULT_HAIKU_MODEL=claude-haiku-5-5 and the Sonnet and Opus equivalents) so haiku means 5.5. No new agent files. 03 · Approaches

Three ways to add the missing six

Recommended

A · Templates first, core last

  • CI-side behaviour (spec job, triage, rehearsal, watch) ships as workflow templates that call claude -p and the vendored sdlc.ts. Zero lines in the checker (templates still count toward the line cap).
  • Approval-gate hooks ship as a managed-settings template, so the core keeps "no hook on Bash" and the enterprise gets the gates where they belong: where engineers cannot switch them off.
  • Core grows by two leaf scripts (evals.ts, watch.ts), metric fields, and edits to three existing skills (start, rule, pr-review). No new skills except one SKILL.md for product owners. Budget: 700 lines, the new cap of 7,600 less today's 6,900.

Why: matches DESIGN §2 ("thin layer, built-ins first") and the ROADMAP rule that optional parts add no imports to check, hooks or sdlc's hot path. Fits the line budget. Each piece is testable on its own.

Alternative

B · Everything in core

  • Evals, detector, gates and deploy become first-class stages in graph.ts with their own nodes.
  • Production gate as a PreToolUse Bash hook in hooks.json.

Rejected: reintroduces the Bash guard layer removed in v0.5.0 for being leaky; adds to the hot path that was just made flat; pushes past the line budget; and the detector would run in every session.

Alternative

C · Separate plugin rig-ops

  • Evals, watch and deploy as a second plugin that reads .sdlc/ evidence.

Deferred: the right shape once the pieces are proven, as ROADMAP says for wiki and learn. Today the pieces are small and standalone repos need them without a second install. Design A keeps them in files that could be split out later without changing interfaces.

05 · Components

Each piece: what it does, how it is used, what it depends on

5.1 Stage 1 · Intent inbox

.sdlc/intent/ (new folder)

The playbook's intent home, next to the code. A product owner or a non-engineer commits intent/<kebab>.md from claude.ai through the GitHub connector. The file follows the p.13 template, checked by the intent-template skill below. Status in frontmatter: draft | accepted | closed. Accepting is a PR merge by the product owner (CODEOWNERS on .sdlc/intent/).

intent-template (new skill)

Vendored like the others, but also usable from claude.ai: a SKILL.md with the organisation's template and the questions an analyst asks (scope, users, constraints, success). disable-model-invocation: false; it writes only the one file. The lead signs off edits to it, through the normal ask rule on skills.

/rig:start reads the inbox (skill edit, no script)

/rig:start intent/<file>: the skill already classifies a request and runs new <slug>; it now accepts an inbox path, takes type and tier from the file's frontmatter when present, copies the body into intent.md and records source: intent/<file>. Six lines of prompt text. pr-checks writes status: shipped back to the inbox file when it already writes ship.json (one line).

Metrics: intent_to_commit_hours (file created → first commit), intent_survival (accepted ÷ (accepted + closed)), intent_edits_after_spec.

5.2 Stage 2 · Policy skills, concerns, spec job

policy-* skills (convention, not code)

.claude/skills/policy-<area>/SKILL.md with two extra frontmatter keys: owner: (a person or team) and source: (the policy's URL or path). The architect agent's brief lists every policy-* skill, so spec.md and design.md are written with them loaded. init scaffolds policy-security from guides/.

## Concerns (design-format change)

templates/design-format.md gains a required ## Concerns section: each line - [policy-<area>] <concern> → owner: <from frontmatter>, or "None". approve design refuses a concern without a resolution line, the same way it refuses open questions today. This is the playbook's "resolve each concern with its policy owner before engineering sees the spec".

rig-spec.yml (new template)

On push to the trunk touching .sdlc/intent/*.md with status: accepted: a job runs claude -p "/rig-start intent/<file>" (the model picked from the file's tier: Haiku S, Sonnet M, Opus L) with --allowedTools limited to Read, Grep, Glob and Edit(.sdlc/changes/<slug>/**), and opens a PR with intent.md and design.md. The product owner's first involvement is the review. Same privilege split as rig-review.yml: the model has no shell or network.

Metric: intent_to_spec_hours (two git timestamps; exists today as plan lead time, renamed and pointed at the design file).

5.3 Stage 3 · The "twice" rule and parallel sessions

/rig:rule gains a prose outcome (skill edit)

/rig:rule already demands two real occurrences before it earns a regex rule. Its step 2 gains a branch: when the recurring mistake cannot be stated as a regex, draft one line for CLAUDE.md's ## Things Claude gets wrong instead, and hand it to the person as it hands over a rule today (the playbook wants code owners to approve CLAUDE.md edits). /rig:pr-review ends with Next: /rig:rule "<category>" when a finding's category appeared on an earlier shipped change.

Metric: repeat_findings, computable from review*.md today.

Parallel sessions (README only)

No code. A README section: status already prints each slice with its files; open one claude --worktree sdlc/<slug>-<n> per group of slices that share no file, 2–3 at a time, and run /rig-build <slug> in each. The slice checkpoint already refuses a file outside the slice's list, so sessions cannot collide. Lane events already count concurrent sessions per engineer.

5.4 Stage 4 · Continuous evals

evals/ (new folder) and sdlc.ts evals

One JSON per eval: { id, prompt, allowedTools, checks: [{ kind: "command" | "file-contains" | "file-absent" | "skill-loaded", ... }], source: "incident:<file>" | "change:<slug>" | "skill:<name>" }. sdlc.ts evals [--only id] runs each with claude -p --output-format json in a throwaway worktree, scores the checks deterministically (captured exit codes, as runs.ts does), and writes .sdlc/evals/<date>.jsonl. The skill-loaded check reads the JSON transcript for a Skill tool call, which is the playbook's "test that the skill triggers".

Seed: sdlc.ts evals --seed drafts 20 evals from the last shipped changes (prompt = intent.md problem, checks = the plan's verification commands). The person curates them.

Manual by decision (no workflow)

A person runs sdlc.ts evals before merging a change to CLAUDE.md, a skill, a hook, the guides, sensors.json or rules.json. Two cheap aids, both existing mechanisms: the harness-tamper sensor's message for those paths gains the sentence "run sdlc.ts evals and attach the result", and status shows the last eval run's pass rate and age. The result file is the evidence the code owner reads in the PR. evals.minPass in sensors.json is advisory: the runner prints pass or fail against it, and nothing blocks on it.

Incident → eval (one step added)

/rig:incident ends by writing evals/incident-<date>-<class>.json with the regression test from diagnose as its check. The eval's source links back to the incident file, so the suite is also the repeat-incident guard.

Metrics: eval_pass_rate (last run, trend), incident_to_eval_hours, regressions_ci_vs_prod (eval failures on PRs ÷ escaped incidents).

5.5 Stage 5 · Review sweep, managed settings, the production gate, CI/CD

/rig:pr-review sweeps to green (skill edit)

The skill's "one fix round" becomes a loop: address unresolved review threads and failing checks, push, wait, repeat until green or ratchet.reviewRounds (default 3). The loop runs in a Haiku subagent, so the main thread's context stays small. Approval stays with the code owner. Uses gh pr view --json reviewThreads,statusCheckRollup and the existing pr-checks. Each round is a lane event, so cost shows per PR.

Metrics: time_to_first_review and comments_resolved_hands_off (exists partly as review metrics today; add the hands-off share).

templates/managed-settings.json (new)

The p.42 JSON with rig's own additions: deny Edit on evidence paths, allow the vendored sdlc.ts, allowManagedHooksOnly: true pointing at templates/gates/, a strictKnownMarketplaces entry for the team's fork, and requiredMinimumVersion. sdlc.ts preflight gains a managed check: reads the effective settings and reports which of the 16 controls are in force (advisory, like the rest of preflight). A per-repo "tailor" block in the file comments names the data classification each deny trades against.

Metric: managed_controls_in_force (n of 16, from preflight; fleet coverage is the admin console's job, not rig's).

templates/production-gate.sh (new, managed hook only)

The p.41 script, verbatim apart from reading the production environment name from an env var the platform team sets. Installed as a PreToolUse Bash hook through managed settings, never through hooks.json: a command naming deploy and that environment needs RELEASE_APPROVAL, else exit 2 with the route to approval. It appends allow or block with a timestamp to .sdlc/gates.jsonl. Protected paths (migrations, infra) need no second hook: put them in the project template's ask rules, where harness-tamper already watches the harness paths.

This keeps rig's core free of Bash hooks (a text match is leaky as a guardrail) while giving the enterprise the gate where it cannot be switched off (managed-only is the control, not the regex).

Metrics: gate_wait_hours from gates.jsonl; gate_violations_escaped from incidents tagged class: gate.

Deploy and rollback (templates only, nothing in rig)

Deploy, status and rollback are MCP tools the platform team registers through managed MCP, scoped per environment; rig holds no deploy config and no credential. Tiered autonomy is then two facts: in dev and staging the agent may call the deploy tool; in production it may call only prepare, and the production gate above blocks the rest. rig-rehearse.yml runs the team's rollback command in staging on a schedule; the metric reads that workflow's run history through gh, so there is no deploys.jsonl to write.

rig-triage.yml (new template)

The p.45 step: on any workflow failure, claude -p --model claude-haiku-5-5 reads the log, says flaky or real, and writes three lines to the PR thread. Read-only tools; a model-free step posts, after the same credential scrub as rig-review.yml. Second stage, behind branch protection: @claude on a comment runs /rig-pr-review through claude-code-action.

Metrics: failures_triaged_without_paging (triage comments ÷ failed runs) and DORA from gh: deployment frequency and lead time from merges and deploy records, change failure rate and time to restore from .sdlc/incidents/ (detected, restored — one new frontmatter field).

5.6 Stage 6 · Closing the loop

sdlc.ts watch (new, deterministic)

Reads bands from sensors.json, one entry per metric: a query (a command that prints a number, e.g. gh run list --json conclusion piped through the script's own counter, or a Prometheus URL), a rolling window, and Western Electric rules. It computes mean and σ over the window from .sdlc/watch/<metric>.jsonl, appends today's point, and prints a tier: 0, 1, 2 or 3. No model. Unit-tested on seeded series. Dismissals (sdlc.ts watch dismiss <id>) widen the band by a configured step, which is the playbook's noise tuning.

"bands": [{
  "id": "ci_failure_rate",
  "query": "gh run list --limit 50 --json conclusion",
  "count": "failure",
  "window": 30, "rules": "western_electric",
  "tiers": {
    "2": { "action": "diagnose", "tools": "Read,Grep,Bash(gh run view *)" },
    "3": { "action": "propose", "routes": ["pull_request", "runbook:rollback"] }
  }
}]
rig-watch.yml (new template)

Scheduled (hourly or daily) or webhook-triggered. Runs sdlc.ts watch; at tier 1 it stops; at tier 2 it runs claude -p --model claude-haiku-5-5 read-only with the band's tools and the diagnosis goes to .sdlc/intent/breach-<id>-<date>.md in the Stage 1 format (status: draft, so a person triages it); at tier 3 it may additionally open a PR through /rig-incident → /rig-diagnose in the same job, or run the named runbook, which is the staging-rehearsed rollback command. Managed settings deny production access; the job's identity is the agent's own.

The existing /rig:incident stays the human entry; the watch job is the headless one. Both end in the same incident file and the same bugfix path.

Metrics: breach_to_intent_hours (exists), findings_merged_share (breach intents that reached ship.json), repeat_incident_share (exists), dismissal_rate per band.

Claude Tag (thin)

Nothing to build. Document in README: when Claude Tag handles an incident in Slack, the on-call engineer runs /rig:incident "<summary>" --escaped and pastes the thread link as evidence; the incident file is the lessons file the playbook describes. A later rig-ops plugin could listen to the channel through an Agent SDK service.

07 · Governance and security

What stays human, what stays deterministic

  • Models never approve. Accepting an intent is a PR merge by the product owner. Design approval, waivers, budget raises and tier changes stay the human-only skills. The review sweep and the watch job open PRs and never merge.
  • The judge cannot be weakened by the judged. Evals are manual, so their guard is review: a PR that edits evals/ and a skill in the same change trips harness-tamper and lands as its own reviewed change, and the eval result the author attaches is evidence the code owner reads, not a verdict a script trusts.
  • No Bash hook in core. The gates are managed-only files. If a team does not deploy managed settings, they have what rig has today, which SECURITY.md already states is guardrails plus CI as the boundary.
  • Headless jobs have the same privilege split as rig-review.yml: the model reads a prepared input and writes one or two named files; a model-free step posts after a credential scrub; secrets never reach fork PRs. The watch job's identity is the agent's own, with no production credential; the only production-affecting route is the pre-approved rollback runbook, rehearsed in staging.
  • Evidence written only by the script: .sdlc/evals/*.jsonl, .sdlc/watch/*.jsonl and .sdlc/gates.jsonl join the deny list in both settings templates.
  • Detection is deterministic. watch.ts has no model call. The tier sets the tools the model may use, and the band config is a protected harness file (ask rule, CODEOWNERS).

09 · Testing

How each piece is proven

  • Unit (node:test, like the rest): watch.spec.ts on seeded series (a slow drift of 8 above the mean trips rule 2 before any 3σ point; a dismissal widens the band); evals.spec.ts with a stubbed claude that returns canned transcripts (skill-loaded detection, exit-code scoring, maxErrors → unmeasured); one case in pr.spec.ts for the inbox status write-back; gate.spec.ts gains a case that runs production-gate.sh with crafted stdin.
  • Integration (the M1 sandbox from tests/integration/): one new scenario per template with the stubbed gh: an accepted intent produces a design PR; a CLAUDE.md edit runs the evals and fails below minPass; a seeded breach writes a draft intent.
  • Size: size.spec.ts cap rises from 6,900 to 7,600 in the same change that adds the first new file. The harness is at 6,900 today, and templates count. Budget for the 700 lines: evals.ts ≤ 170, watch.ts ≤ 150, metrics +60, preflight +25, skill edits +30, the model field and skill edits +15, production-gate.sh +15, managed-settings.json +45, four workflow templates (spec, triage, rehearse, watch) ≤ 45 each. The implementation plan carries this table and the size test fails the build if it slips.
  • Live: one paid run per template on the shop-app lane before a release, as the release integration test proposal does.

11 · Decisions

Answered on 2026-10-07

  1. Core or plugin: core. The line cap rises to 7,600 (the harness is at 6,900 today and templates count), which leaves exactly the 700 lines §9 budgets.
  2. Evals: manual. No workflow, no schedule; a person runs sdlc.ts evals before merging a config change and attaches the result.
