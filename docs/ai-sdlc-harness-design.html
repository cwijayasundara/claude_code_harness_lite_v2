Design · 2026-10-07 · decisions taken, ready for planning

Closing the gaps between rig and the AI-Native SDLC Playbook

rig v0.6.0 already implements the playbook's core: the artifact chain, type × tier routing, human-only gates, deterministic sensors, a CI judge that cannot be weakened by the PR it judges, and the twelve metrics. This design maps every checklist item in docs/ai-sdlc-checklist.md to what rig has, and designs only what is missing. It keeps rig's principles, adds nothing to the core checker that a CI template can carry, and respects the 6,900-line budget.

01 · Understanding (please correct)

What this is for

Goal
Make a repo onboarded with rig satisfy every item in the checklist, including the worked example on p.42–43, CI/CD, and maintenance, so a team can run the playbook end to end on Claude Code.
Who
Engineering teams using rig, and a platform team that deploys managed settings and CI.
Success
Every checklist row reads covered with a named component, and every playbook metric is computed by sdlc.ts metrics rather than estimated.
Constraints you gave
Keep rig as simple and lean as possible. Every item below passes a lean test: it is a template (zero core lines), a change to an existing skill, or a leaf script under 200 lines; anything else is cut or deferred. Model by tier: tier S on Haiku 5.5 (claude-haiku-5-5, $0.10 in / $0.50 out per M tokens), tier M on Sonnet 5.5, tier L on Opus 5.5, for every model step of a change (design, implementation, review, CI review, spec job). Steps that are not tied to a change (code search, triage, watch diagnosis, the review sweep) run on Haiku.
Decisions taken
(1) Everything lands in core; the line cap rises from 6,900 to 7,600, and the design must fit it, templates included, because size.spec.ts counts them. (2) Evals are run by a person, never on a schedule or a PR trigger. (3) The intent inbox is .sdlc/intent/. (4) Model by tier, as above. (5) The production gate may match command text, as the playbook's script does.
Constraints I assume
No hook on Bash in the core (DESIGN §9). New parts add no imports to check, hooks or sdlc's hot path (ROADMAP's v3 rule). Windows stays unsupported. Claude Tag (Slack) is a thin integration, not a dependency.
Not in scope
The DeepWiki and learning loops from ROADMAP.md. A rewrite of any existing stage. Moving artifacts out of .sdlc/.

Six items are real gaps. Under the lean rule, only two of them need code in rig (evals.ts and watch.ts, both leaf scripts); the other four are templates, one SKILL.md, and edits to skills that already exist.

Model routing: one rule, tier picks the model

Decision 4: S → Haiku 5.5, M → Sonnet 5.5, L (and greenfield) → Opus 5.5, applied to every model step that belongs to a change. The mechanism is one thing rig does not do today: agents carry a fixed model:, and no skill sets one (a model switch re-reads the context uncached, DESIGN §2.7). The mechanism is the Agent call's own model parameter, which rig already uses (the build skill's tier L slice review passes model: sonnet) and which takes precedence over an agent file's model:. sdlc.ts next --json gains a model field derived from the change's effective tier; every skill passes it on each architect, implementer and reviewer launch. The template pins the aliases (ANTHROPIC_DEFAULT_HAIKU_MODEL=claude-haiku-5-5 and the Sonnet and Opus equivalents) so haiku means 5.5. No new agent files. 03 · Approaches

Three ways to add the missing six

Recommended

A · Templates first, core last

  • CI-side behaviour (spec job, triage, rehearsal, watch) ships as workflow templates that call claude -p and the vendored sdlc.ts. Zero lines in the checker (templates still count toward the line cap).
  • Approval-gate hooks ship as a managed-settings template, so the core keeps "no hook on Bash" and the enterprise gets the gates where they belong: where engineers cannot switch them off.
  • Core grows by two leaf scripts (evals.ts, watch.ts), metric fields, and edits to three existing skills (start, rule, pr-review). No new skills except one SKILL.md for product owners. Budget: 700 lines, the new cap of 7,600 less today's 6,900.

Why: matches DESIGN §2 ("thin layer, built-ins first") and the ROADMAP rule that optional parts add no imports to check, hooks or sdlc's hot path. Fits the line budget. Each piece is testable on its own.

Alternative

B · Everything in core

  • Evals, detector, gates and deploy become first-class stages in graph.ts with their own nodes.
  • Production gate as a PreToolUse Bash hook in hooks.json.

Rejected: reintroduces the Bash guard layer removed in v0.5.0 for being leaky; adds to the hot path that was just made flat; pushes past the line budget; and the detector would run in every session.

Alternative

C · Separate plugin rig-ops

  • Evals, watch and deploy as a second plugin that reads .sdlc/ evidence.

Deferred: the right shape once the pieces are proven, as ROADMAP says for wiki and learn. Today the pieces are small and standalone repos need them without a second install. Design A keeps them in files that could be split out later without changing interfaces.

5.1 Stage 1 · Intent inbox

.sdlc/intent/ (new folder)

The playbook's intent home, next to the code. A product owner or a non-engineer commits intent/<kebab>.md from claude.ai through the GitHub connector. The file follows the p.13 template, checked by the intent-template skill below. Status in frontmatter: draft | accepted | closed. Accepting is a PR merge by the product owner (CODEOWNERS on .sdlc/intent/).

intent-template (new skill)

Vendored like the others, but also usable from claude.ai: a SKILL.md with the organisation's template and the questions an analyst asks (scope, users, constraints, success). disable-model-invocation: false; it writes only the one file. The lead signs off edits to it, through the normal ask rule on skills.

/rig:start reads the inbox (skill edit, no script)

Revised 2026-10-08 during M2 planning: a small leaf script, scripts/inbox.ts (sdlc.ts inbox [--pending] [--json]), derives each inbox entry's state, because four consumers need it (status, metrics, the spec workflow's selection and its model choice); shipped is derived, never written back. /rig:start intent/<file>: the skill already classifies a request and runs new <slug>; it now accepts an inbox path, takes type and tier from the file's frontmatter when present, copies the body into intent.md and records source: intent/<file>. Six lines of prompt text. shipped is derived, not written: an inbox file counts as shipped once the change that names it as source: has shipped.
